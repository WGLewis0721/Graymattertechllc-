# Reference Case Study | Listening Room (Fictional Demo)

**Purpose:** One complete, working example of the quality bar this library describes, so a new project can be compared against something real: what was built, in what order, how each phase was proven, what was real and what was simulated, and where the working code lives. It is a **worked example, not a template to install**, and it contains no client facts: the DJs, venue and event are fictional demo content created by the library owner.

**Source:** [WGLewis0721/Listening-party-](https://github.com/WGLewis0721/Listening-party-), inspected at [commit 71aeb25](https://github.com/WGLewis0721/Listening-party-/tree/71aeb25). Its own [BUILD-PLAYBOOK.md](https://github.com/WGLewis0721/Listening-party-/blob/71aeb25/BUILD-PLAYBOOK.md) is the long-form handoff recap. Labels: **[Repo]** verified at that commit; **[Not tested]** not run.

## 1. What it is

A one-page, scroll-animated, **hero-only** promo site for a monthly DJ listening party, plus a customer ticket card in the same look, a client concept-review page, a door check-in tool and a server scaffold. It is customizable per DJ, aesthetic and set list through one config file, and it ships in **five complete looks** from one frame.

## 4. Order of work (reuse this sequence)

1. **Intake:** turn the source material (here, a screenshot of an event post) into numbered requirements; set the repo rule (fictional names only).
2. **Research** the category; write down what to borrow and what not to.
3. **Brand system:** frame, skin, guardrails as numbers.
4. **Wireframes and the requirements-to-interface map.**
5. **Engine:** config object, hero, shaders, ticket card, pay page; static fallback from the start.
6. **Looks:** four more skins by copying one edition and editing its config.
7. **Verify by script** (scroll states, contrast over art, sizes, overflow, console, Reduce Motion) and fix what it finds.
8. **Deploy** early (GitHub Pages workflow) and test the live URL.
9. **Client review site:** picker, in-place skin switcher, card generator, favorite and note.
10. **Secure the flow:** threat model, simulator first, then the server, then database and concurrency tests.
11. **Simplify** for people with no time; add the plain-language, first-screen and door checks.
12. **Plumbing and the gate:** share tags, sitemap, policy, plain pages, deploy gate; test the built site under the production sub-path and then the live site.
13. **Distribute:** a client message, a public post, link tips; record the handoff.

Between phases the agent committed in reviewable steps, tracked a task list, reported pass or total counts, and wrote down what was **not** verified.

## 7. Honest limits

- It is one project, built by one person working with an AI agent. The patterns are proven *there*; adapt them, do not assume they transfer unchanged.
- Everything is a **desktop headless-browser** result plus database and unit tests. Phones, assistive technology and real users have not tested it.
- Third-party libraries (GSAP and ScrollTrigger under the vendor's standard license, qrcode.js under MIT, jsQR under Apache-2.0) are vendored with their licenses recorded; **review the terms yourself** before reuse.
